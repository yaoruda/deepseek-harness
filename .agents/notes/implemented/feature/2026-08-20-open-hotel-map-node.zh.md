# Agent Note: 开放酒店地图节点

Status: implemented

[English](2026-08-20-open-hotel-map-node.md) | 中文

## 问题

纯文字酒店推荐无法展示空间关系，也无法把每个候选酒店与同一个目的地比较。Skill 可以协调调用，但不能增加可重放的交互地图；文字路线估计还会丢失来源状态和路线几何。

## 决策

`@deepseek-ai/dsh-tool-hotel-map` 通过可配置的 Nominatim、OSRM 和 Transitous 兼容端点注册一个有上限的 `hotel_map` 工具。工具接收已知酒店地址，可选解析一个目的地，并只在所有服务请求结束后追加一条完整的 `travel-map/show` 事件。部分失败不会删除酒店。路线结果区分 `available`、`unavailable` 和 `failed`；公交数据缺口不会被表达为当地没有公交。

`@deepseek-ai/dsh-client-ui-hotel-map` 提供一个带 key 的聊天 Conversation Node。它从持久化事件渲染标点、选中的驾车或公交路线几何、时长、距离、未解析地址和服务署名。历史重放不会再次请求地址或路线服务。地图瓦片仍由浏览器请求，因为事件不持久化第三方栅格数据。

随附组合选择低频公共社区端点，按可配置间隔串行解析地址，发送可识别的 User-Agent，并在进程内缓存成功坐标。所有端点均可配置，因此部署可以在不修改工具或 Skill 的情况下切换到自建服务。

## 考虑过的替代方案

**付费全球 API。** Google Maps Platform 的集成覆盖更强，但要求凭据和按量计费，无法形成零密钥可分发 Skill。

**只有 Skill，没有产品代码。** 指令可以让 Agent 收集地址并调用通用网页工具，但无法引入类型化结果、持久化地图事件或浏览器渲染器。

**通用工具卡或 Markdown iframe。** 现有卡片没有地图渲染意图。iframe 会依赖外部页面状态，削弱重放，也不能表达酒店和路线之间的类型化关系。

**只使用自建 OpenTripPlanner。** 它能提供更强的部署控制，但需要按地区构建 OpenStreetMap 和 GTFS 图。兼容服务的配置保留了自建路径，同时不把它设为首次使用的前提。

## 后果

功能无需 API Key，可以随开源 Skill 分发，但社区服务按尽力原则提供，使用政策会限制规模。公交覆盖取决于公开时刻表。客户端因内联 MapLibre 而增大，初始栅格瓦片 URL 在高频分发前还需要增加配置路径。

聚焦服务测试固定了响应归一化和无可用行程行为。客户端 Definition 测试固定了完整事件重放。包 README 的限制部分保存了社区容量、覆盖、缓存生命周期、酒店交易数据、瓦片、包体积和离线地图缺口。
